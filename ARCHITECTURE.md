# Архитектура ExeScope и перечень реальных ограничений

ExeScope — специализированный инструмент наблюдения и динамического анализа подозрительных исполняемых файлов Windows в изолированных тестовых средах.

---

## 2. Реальные технические ограничения и их обработка

### Ограничение 1: Привилегии Windows (Administrator vs Standard User)
* **Реальность:** Трассировка событий ядра через Windows Kernel ETW (`Microsoft-Windows-Kernel-File`, `Registry`, `Network`) требует привилегий локального администратора.
* **Решение в ExeScope:** 
  * Интерфейс по умолчанию запускается в пользовательском контексте (`asInvoker` в `app.manifest`).
  * При запуске модуль проверяет роль администратора.
  * Если права администратора отсутствуют:
    * Приложение **не падает и не скрывает проблему**.
    * В строке состояния и журнале диагностики выводится четкое предупреждение.
    * Включается стандартный отказоустойчивый режим (Standard User Fallback):
      * Иерархия процессов отслеживается через `Toolhelp32` и `Process.GetProcesses()`.
      * Сетевые TCP/UDP соединения связываются с PID через документированный Win32 IP Helper API (`GetExtendedTcpTable` / `GetExtendedUdpTable`).
      * Сохранение артефактов из контролируемых каталогов (%TEMP%, AppData, папка образца) продолжает функционировать.

### Ограничение 2: Переиспользование PID в Windows (PID Recycling)
* **Реальность:** Windows активно и быстро переиспользует числовые идентификаторы процессов (PID) сразу после завершения процесса и закрытия всех описателей (`HANDLE`). Фильтрация только по номеру PID приводит к ложной привязке чужих событий.
* **Решение в ExeScope:** 
  * Идентификатором процесса является пара `(PID, StartTimeUtc)`.
  * Движок корреляции `ProcessCorrelationEngine` проверяет, попадает ли временная метка события в интервал жизни отслеживаемого процесса `[StartTimeUtc, ExitTimeUtc + 2s]`.
  * Повторно созданные несвязанные процессы с тем же PID игнорируются.

### Ограничение 3: Разделение журнала операций и содержимого файлов
* **Реальность:** События файловой системы в ETW фиксируют факт операции (создание, чтение, запись, смещение, размер, статус), но драйвер файловой системы не передает в трассировку полные прочитанные байты (это вызвало бы переполнение буферов памяти и диска за секунды).
* **Решение в ExeScope:**
  * События `FileEvent` явно содержат флаг `HasCapturedBytes = false`.
  * Для сохранения файлов используется компонент `FileArtifactCollector`:
    * Сохраняются только файлы, **созданные или изменённые** исследуемыми процессами.
    * Действует белый список каталогов (по умолчанию исключаются системные каталоги Windows и Program Files, чтобы не копировать гигабайты системных DLL).
    * Действуют строгие лимиты на максимальный размер отдельного файла (по умолчанию 10 МБ) и общий бюджет сессии (по умолчанию 100 МБ).
    * Копирование выполняется в неблокирующем режиме с флагами `FileShare.ReadWrite | FileShare.Delete`.
    * Если файл был изменён во время копирования, выставляется флаг `MightHaveChangedDuringCopy`.
    * Если файл заблокирован монопольно или удален до копирования, фиксируется причина ошибки в `artifacts-index.jsonl`.

### Ограничение 4: Сетевой захват и приватность (PCAPNG)
* **Реальность:** Перехват сырых сетевых пакетов (Raw Sockets / Promiscuous mode) на уровне ОС видит трафик всей машины, включая посторонние службы и фоновые процессы.
* **Решение в ExeScope:**
  * Захват пакетов по умолчанию **выключен**. При попытке включения пользователю отображается подробное диалоговое окно с предупреждением.
  * Модуль `RawSocketCapture` выполняет строгую фильтрацию: сохраняются только пакеты, локальный порт которых принадлежит отслеживаемым процессам.
  * Для TLS/HTTPS сохраняются только зашифрованные пакеты и метаданные. Приложение **не устанавливает поддельные корневые сертификаты** и **не выполняет MITM-перехват**.

### Ограничение 5: Безопасность путей (Path Traversal Protection)
* **Реальность:** Подозрительное приложение может создавать файлы с именами вроде `../../evil.bat`, именами потоков NTFS (`file.txt:hidden`) или зарезервированными именами DOS (`CON`, `NUL`, `COM1`).
* **Решение в ExeScope:**
  * Модуль `PathSanitizer` валидирует и очищает все имена файлов.
  * Запрещенные последовательности заменяются безопасными подчеркиваниями.
  * Метод `CreateSafeArtifactDestination` проверяет канонический путь и гарантирует, что целевой файл физически находится внутри `<SessionDir>/artifacts/`. Любая попытка выхода за пределы каталога пресекается с исключением.

## 3. Модель потокобезопасности и буферизации

1. **Неблокирующая очередь событий (`BoundedChannelQueue<T>`):**
   * Все сборщики событий отправляют события в ограниченный канал `System.Threading.Channels.Channel<T>`.
   * При перегрузке или лавине событий очередь отбрасывает старые события (`DropOldest`) и атомарно инкрементирует счетчик потерь.
   * Количество потерянных событий непрерывно отображается в интерфейсе и фиксируется в отчёте.

2. **Пакетная асинхронная запись на диск:**
   * Фоновый потребитель сбрасывает события в файл `events.jsonl` пачками до 100 событий либо по таймеру 500 мс.
   * Это предотвращает блокирование потока сбора событий и GUI.

3. **Изоляция пользовательского интерфейса:**
   * Интерфейс WPF не осуществляет прямых дисковых или системных опросов в основном потоке.
   * Все обновления коллекций происходят через асинхронный диспетчер с низким приоритетом (`DispatcherPriority.Background`).
